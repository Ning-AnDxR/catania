我刚开始做卡坦岛时，最容易犯的错误是先把注意力放在页面和按钮上。会想先画棋盘、先做开始页面、先做点击动画。但真正开始以后我才发现，页面只是玩家看到的结果，游戏真正的核心是“玩家做了什么事情，规则是否允许，允许以后状态发生了什么变化，界面应该根据什么变化更新”。这篇文档记录我从理解游戏业务逻辑、认识状态机，到完成第一阶段和规划后续开发的整个过程。

一、先不要问页面怎么写，先问玩家动作发生了什么

以初始放置定居点为例。玩家点击棋盘上的一个交点时，表面上看只是一个点击事件，但业务上至少包含下面这些问题：

  • 现在轮到这个玩家了吗？
  • 当前处于第一轮还是第二轮初始放置？
  • 当前应该先放定居点还是先放道路？
  • 这个交点是不是已经有人占领？
  • 相邻交点有没有其他建筑？
  • 如果是第二轮，玩家应该获得哪些初始资源？

只要这些问题没有统一答案，前端和后端就很容易各写一套逻辑，最后出现“页面看起来能点，但规则状态已经乱了”的情况。所以我把一个动作拆成下面的路径：

玩家操作
-> Command
-> 规则校验
-> 状态变化
-> Event
-> UI 更新

这里的 Command 表示“玩家想做什么”，Event 表示“系统确认发生了什么”。它们不是同一个东西，也不能互相替代。

二、状态机不是装饰，它决定什么时候允许做什么

状态机在项目里的作用，是限制游戏只能按照合法顺序前进。第一阶段的状态是：

LOBBY
-> SETUP_ROUND_1
-> SETUP_ROUND_2
-> AWAITING_ROLL

在 LOBBY 阶段只能开始游戏。在第一轮和第二轮初始放置阶段，只能按照当前玩家的顺序放置定居点和道路。初始放置完成后，状态进入 AWAITING_ROLL，表示接下来应该掷骰子。

如果没有状态机，代码里会出现很多零散判断，例如“按钮禁用条件”“玩家能不能点”“什么时候切换回合”。这些判断会散落在不同组件里。状态机的价值是把它们集中到规则引擎中。前端只负责展示当前合法动作，真正是否允许执行，仍由状态机判断。

我目前用一个 Command 表示一次请求，用一次版本递增表示一次成功更新。一个 Command 可以产生多个 Event，例如放置第二个定居点时会同时产生：

SETTLEMENT_PLACED
RESOURCES_GAINED
VICTORY_POINTS_CHANGED

如果命令不合法，则状态完全不改变，并返回明确错误，例如：

NOT_YOUR_TURN
DISTANCE_RULE_VIOLATION
ROAD_NOT_CONNECTED

三、把桌游动作翻译成数据

理解业务逻辑以后，下一步不是直接写界面，而是把桌游动作翻译成命令。第一阶段实际使用了三个命令：

START_GAME
PLACE_INITIAL_SETTLEMENT
PLACE_INITIAL_ROAD

以放置定居点为例，一个命令信封可以写成：

{
  commandId: "command-001",
  gameId: "game-001",
  actorId: 0,
  expectedVersion: 7,
  command: {
    type: "PLACE_INITIAL_SETTLEMENT",
    vertexId: 12
  }
}

规则引擎先检查版本，再检查玩家、阶段、当前步骤、顶点是否为空以及距离规则。全部通过后，才修改状态并产生事件。只要坚持“先校验，再执行”，后续加入建造、强盗、发展卡和交易时，就不会因为动作越来越多而失去控制。

四、第一阶段应该做到什么程度

第一阶段的目标不是做完整卡坦岛，而是验证整个项目的地基。因此我把它限制为下面这些内容：

  • 生成标准 19 格地图。
  • 建立 54 个顶点和 72 条边的共享图结构。
  • 生成地形、数字令牌和 9 个港口。
  • 支持三名或四名玩家。
  • 实现蛇形初始放置顺序。
  • 校验定居点距离规则。
  • 校验初始道路必须连接刚放置的定居点。
  • 第二轮定居点发放相邻资源。
  • 用随机 AI 自动完成初始放置。
  • 记录 Command 和 Event，方便观察整个过程。
  • 最后进入 AWAITING_ROLL。

第一阶段暂时不做掷骰、建造、强盗、发展卡、贸易和 WebSocket。因为如果这些功能一起加入，一旦状态出错，很难判断是棋盘图、回合流程还是规则引擎的问题。

五、四个开源项目分别借鉴了什么

我没有把四个项目依次照抄，而是先选一个主干，再按不同用途查阅。四人的分工如下：

项目许可证借鉴内容
hex-catan-multiplayerMIT共享顶点和边、阶段划分、事件日志、Bot 命令入口、未来 WebSocket 结构
settlers-of-the-island无 LICENSE仅研究蛇形初始放置、第二轮资源和轻量单机流程
catan-3d无 LICENSE仅研究六边形坐标、角点转共享顶点以及渲染和规则分离
catanatronGPL-3.0研究初始建造阶段、第二定居点资源和端到端流程测试

具体实现时，我使用了自己的命名、状态结构和测试。无许可证项目只作为学习材料，没有直接复制代码。catanatron 使用 GPL-3.0，如果后续直接复用它的代码，需要重新评估整个项目的开源要求。

六、第一阶段如何落地

项目先分成规则、AI、调试界面和测试四部分。核心规则不依赖页面，因此以后换成正式 UI 或 WebSocket 服务端时，不需要重写棋盘和初始放置。

Catan
|- src/core
|  |- board.js
|  |- engine.js
|  |- session.js
|  |- projection.js
|  |- constants.js
|  |- state.js
|- src/bots
|  |- random-bot.js
|- debug
|  |- index.html
|  |- app.js
|- tests
   |- board.test.js
   |- setup.test.js
   |- random-bot.test.js

棋盘生成的关键不是画六边形，而是建立一个共享图。每个地块根据六个角计算顶点；距离相同的角合并成同一个顶点；相邻顶点之间生成一条边。这样后续判断定居点距离和道路连接时，不需要做坐标距离计算，只需要查询图结构。

初始放置顺序使用：

0, 1, 2, 3, 3, 2, 1, 0

每个位置包含一次定居点放置和一次道路放置。第二轮放置定居点时，读取该顶点相邻的地块，为每个资源地块增加一张对应资源。

AI 当前只做随机合法选择。它从 PlayerView 中的 validCommands 选择命令，再交给同一个规则引擎。AI 不直接改状态，这一点非常重要，因为以后无论是人类、本地 AI 还是服务器 Bot，都使用同一条命令路径。

七、如何验证第一阶段真的完成了

我没有只看页面是否显示棋盘，而是同时用自动化测试和浏览器实际操作验证。测试覆盖：

  • 地图是否包含 19 个地块、54 个顶点、72 条边和 9 个港口。
  • 相同种子是否得到相同地图。
  • 同一玩家顺序是否正确。
  • 是否拒绝非法回合。
  • 是否拒绝没有连接定居点的道路。
  • 是否拒绝违反距离规则的定居点。
  • 第二轮是否获得正确数量的初始资源。
  • 版本冲突是否不会修改状态。
  • 随机 AI 是否能完整完成初始放置。

浏览器实测中，玩家和三个 AI 都完成了两个定居点和两条道路，最终状态为 AWAITING_ROLL。控制台没有错误，说明规则层和调试 UI 已经能配合工作。

八、第二阶段：先把“一个完整回合”跑通

第一阶段把状态送到 AWAITING_ROLL 后，我一度想直接开始做建造。但很快发现，AWAITING_ROLL 只证明初始放置已经结束，还没有证明游戏能持续运转。第二阶段不应该继续堆新机制，而要把最基础的回合循环做成闭环：

AWAITING_ROLL
-> ROLL_DICE
-> DICE_ROLLED
-> RESOURCES_PRODUCED
-> TURN_ACTIONS
-> END_TURN
-> TURN_STARTED
-> AWAITING_ROLL

这条路径暂时不处理点数 7 的完整规则。7 会引出弃牌、移动强盗和偷取资源，流程会从一个线性回合分裂成多个等待状态。第二阶段先给 7 留出明确分支，但不在这一阶段展开；等正常点数的资源生产和换人流程稳定后，再单独接入强盗系统。

1. 第二阶段只增加两个命令

为了让回合循环足够小，第二阶段只新增两个命令：

ROLL_DICE
END_TURN

ROLL_DICE 只负责判断当前玩家能否掷骰，并通过注入的随机数生成器产生两个骰子。END_TURN 只负责结束当前玩家回合，切换到下一位玩家并重置回合状态。建造、购买发展卡、贸易都不放进这两个命令里。状态机新增 TURN_ACTIONS，表示本回合已经掷骰并完成资源结算；在第二阶段里，这个阶段只允许 END_TURN。

2. ROLL_DICE 先校验，再产生结果

掷骰看起来只是一个随机数问题，但业务上仍要按 Command 的路径处理。只有当 actorId 等于当前玩家、阶段为 AWAITING_ROLL、本回合尚未掷骰，并且 expectedVersion 与状态一致时，命令才会被接受。失败时分别返回明确错误：

NOT_YOUR_TURN
INVALID_PHASE
ALREADY_ROLLED
VERSION_CONFLICT

通过校验后，规则引擎才修改状态：记录两个骰子、总点数和本回合已经掷骰，再追加 DICE_ROLLED。资源生产不是一个独立按钮，而是这次掷骰成功后的后半段结算。这样即使以后加入动画，界面也只能根据事件播放结果，不能自己重新计算一次点数。

3. 资源生产要先汇总，再发放

RESOURCES_PRODUCED 不能简单地看到一个地块就立即发牌。我的处理顺序是：

  1. 用两个骰子的总点数找到所有数字令牌相同的资源地块。
  2. 扫描这些地块的相邻顶点，定居点记 1 份需求，城市记 2 份需求。
  3. 先按资源类型汇总整次掷骰的需求，而不是一块地一块地直接扣银行。
  4. 如果银行库存足够，再统一扣除银行并增加玩家手牌；如果某一种资源的库存不足，则这次掷骰中该资源没有人获得，并产生 BANK_RESOURCE_SHORTAGE。
  5. 发放时固定按照地块编号和玩家编号排序，保证相同种子、相同事件重放得到相同结果。

这里容易出现一个隐蔽错误：先给前面玩家发了资源，后面才发现银行不够。这样会让结果依赖玩家顺序。先汇总、再一次性决定是否发放，才能保证资源守恒，也更容易测试。每次成功发放都要同时产生公开的 RESOURCES_PRODUCED 和对应玩家可见的 HAND_CHANGED，公开事件只说明哪个地块生产了什么，不泄露其他玩家的完整手牌。

4. 回合状态要单独保存

为了区分“这一局进行到哪里”和“当前玩家这一回合进行到哪里”，状态里需要单独记录回合信息，例如：

turn: {
  hasRolled: false,
  dice: null,
  production: []
}

hasRolled 决定 ROLL_DICE 是否还能执行，dice 保存本次点数，production 保存已经结算过的生产摘要。它们必须在 END_TURN 时一起重置。PlayerView 不需要下发整个权威状态，只需要根据当前玩家生成 validCommands：轮到谁，谁就收到 ROLL_DICE；进入 TURN_ACTIONS 后，当前玩家收到 END_TURN。界面只展示这些合法动作，不再自己写一套“按钮什么时候可以点”的判断。

5. END_TURN 要完成一次事务

END_TURN 通过校验后，规则引擎按下面的顺序完成一次原子更新：

TURN_ENDED
-> 切换 currentPlayerId
-> 重置 hasRolled 和 dice
-> TURN_STARTED
-> PHASE_CHANGED: TURN_ACTIONS -> AWAITING_ROLL

这里我把 turnNumber 定义成“第几轮”，而不是“第几个玩家动作”。当前玩家从最后一位切回第一位时，才增加 turnNumber；同一轮内换人只改变 currentPlayerId。一个 END_TURN 命令只增加一次版本号，产生的多个事件共享这个版本，但按 sequence 保持顺序。这样事件日志既能表示一次完整事务，也能支持以后按版本增量同步。

6. 第二阶段必须覆盖的测试

  • 不是当前玩家时，ROLL_DICE 被拒绝且状态不变。
  • 同一玩家在同一回合连续掷骰两次时，第二次返回 ALREADY_ROLLED。
  • 固定骰子结果时，只让数字令牌匹配的地块生产资源。
  • 定居点获得 1 份资源，城市获得 2 份资源。
  • 沙漠地块和点数不匹配的地块不生产资源。
  • 银行库存不足时，该资源本次掷骰不发放给任何玩家。
  • 每次生产前后的银行库存与玩家手牌总量守恒。
  • END_TURN 后正确切换玩家、重置回合状态并回到 AWAITING_ROLL。
  • 四名玩家连续完成多轮回合，不会卡死在 TURN_ACTIONS。
  • 记录的事件全部重放后，得到的状态与直接执行命令后的状态一致。

7. 第二阶段完成的标准

当玩家和 AI 可以连续玩若干轮，随机掷骰都能进入资源生产并顺利换人；银行资源不会凭空增加或丢失；任何一次资源变化都能在事件日志中找到原因；前端刷新后仍能按版本恢复一致状态，第二阶段才算完成。

到这时再接入建造道路、定居点和城市，新的命令只是进入 TURN_ACTIONS 这个阶段，而不是推翻回合循环。之后再加入点数 7、弃牌、移动强盗和偷取资源，发展卡和玩家间交易放在更后面。联机版也继续保持同样的命令和事件边界：单机使用 LocalGameSession，未来替换为 RemoteGameSession，服务器负责校验并广播事件或状态变更。

九、我目前的理解

做一个卡坦岛，不只是把桌游规则翻译成代码。更有价值的是把规则整理成状态、命令和事件，让任何一次操作都能回答三个问题：玩家想做什么，规则是否允许，执行后发生了什么变化。

只要这三个问题清晰，前端可以替换，AI 可以增强，单机可以升级为 WebSocket 联机，而核心规则不需要重写。第一阶段完成以后，我对下一阶段的关键任务也更清楚了：先把掷骰和资源生产做成一个完整、可测试、可回放的回合闭环，再继续增加更多卡坦岛机制。
